# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A PlatformIO project for a Seeed Xiao ESP32-C6, built on **ESP-IDF directly** (`framework = espidf` in `platformio.ini`) — not Arduino. There is no `Serial`, no `setup()`/`loop()` Arduino entry points, and no Arduino libraries available unless explicitly added. Entry point is `extern "C" void app_main(void)` in `src/main.cpp`.

Three DS18B20 sensors are connected to GPIO21. Temperature measurements are read every `SENSOR_READ_INTERVAL_MS` (30s, in `main.cpp`) and each published as its own JSON MQTT message.

## Commands

This is a PlatformIO/ESP-IDF project, not Arduino — build/flash/monitor via `pio`, not the Arduino IDE.

```sh
pio run                    # build
pio run --target upload    # flash to the connected board
pio device monitor         # serial monitor (115200 baud, matches monitor_speed)
pio run --target upload --target monitor   # flash then monitor in one step
pio run --target clean     # clean build artifacts
```

No unit tests, no linter is configured (`test/` is an empty PlatformIO placeholder). Verification is hardware-flashing only — do not add test scaffolding or a linter setup.

## Required local config (gitignored, not present in a fresh checkout)

Two headers under `include/` must be copied from their `.example.h` counterparts and filled in before this builds/connects to anything real:
- `include/wifi_config.h` ← `wifi_config.example.h` (`WIFI_SSID`, `WIFI_PASSWORD`)
- `include/mqtt_broker_config.h` ← `mqtt_broker_config.example.h` (broker host/port/credentials, TLS mode, mutual-TLS cert/key, `MQTT_TOPIC_HEARTBEAT`, `MQTT_TOPIC_SENSOR`)

Both real files are gitignored specifically so credentials/certs never get committed. When touching MQTT or WiFi setup, treat the `.example.h` file as the source of truth for what config keys exist and update both files together if adding a new config key.

## Architecture

Flat `src/` layout, one module per concern, each following `<module>_setup()` as its public entry point (per user's embedded conventions):

- **`main.cpp`** — `app_main()`: brings up WiFi, then MQTT, publishes an initial heartbeat, sets up the DS18B20 sensors, then loops forever polling every `COMMAND_POLL_INTERVAL_MS` (100ms), re-publishing a heartbeat every `HEARTBEAT_INTERVAL_MINUTES` (90 min) and reading+publishing all sensors every `SENSOR_READ_INTERVAL_MS` (30s).
- **`wifi_manager`** — blocks in `wifi_manager_setup()` until the STA link is up or permanently failed (retries up to `WIFI_MAXIMUM_RETRY`), using an `EventGroupHandle_t` + `esp_event` handlers. Explicitly disables modem-sleep (`WIFI_PS_NONE`) since the device is mains-powered and power-save causes MQTT-disrupting reassociation cycles.
- **`mqtt_client_manager`** — builds the broker URI (`mqtts://` vs `mqtt://` based on `MQTT_BROKER_USE_TLS`), configures TLS (server cert verification is optional via `MQTT_BROKER_VERIFY_CERTIFICATE`; mutual-TLS client cert/key are always presented when TLS is on), and blocks in `mqtt_client_manager_setup()` until connected or timed out. `mqtt_client_manager_publish_heartbeat()` and `mqtt_client_manager_publish_sensor_reading()` build their JSON payloads manually via `snprintf` (no JSON library) and publish at QoS 1.
- **`device_identity`** — derives a stable `MCUDEVICE-<mac>` device ID from the factory-programmed efuse MAC (byte order reversed to match the existing device fleet's convention — this reversal is deliberate, not a bug) and a colon-separated MAC string from the active WiFi MAC.
- **`ds18b20_sensor`** — wraps the `espressif/onewire_bus` + `espressif/ds18b20` components. `ds18b20_sensor_setup()` brings up a 1-Wire bus on GPIO21 (RMT backend) and enumerates up to `DS18B20_SENSOR_MAX_COUNT` (3) devices at startup — sensor index is assignment order from that one-time bus scan, not a physical/serial-number mapping, so swapping which physical sensor is "index 0/1/2" means re-flashing, not reconfiguring. `ds18b20_sensor_read_all()` triggers a conversion for all sensors and invokes a callback per successful reading; failed reads (bad CRC, etc.) are logged and skipped rather than retried.

### Known leftovers from the sibling relay-control project this was based on

`mqtt_client_manager.cpp` creates an unused length-1 command queue (`s_command_queue`) with a comment about "desired relay state", and `CMakeLists.txt` still names the project `seeed-relay-control`. Don't assume the queue is wired to anything; check before building on it.

### Dependencies

`src/idf_component.yml` pulls in `espressif/mqtt`, `espressif/onewire_bus`, and `espressif/ds18b20` (ESP-IDF component registry) alongside the IDF framework itself; resolved versions are pinned in `dependencies.lock` (regenerated by `pio run`, don't hand-edit). `managed_components/` is where these get vendored in at build time — generated, not hand-edited. Each managed component must also be listed in `src/CMakeLists.txt`'s `PRIV_REQUIRES` (by its bare component name, e.g. `ds18b20`, not the `espressif/` registry prefix) or its headers won't resolve.
